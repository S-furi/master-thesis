\chapter{Implementation and Evaluation}\label{ch:impl_eval}

\section{The Reactive Framework}
Building upon the design principles established in
\Cref{ssec:reactive_alchemist_principles} and the architectural analysis in
\Cref{ssec:in_house}, this section presents the concrete implementation of the
proposed reactive solution. The framework is designed around a lightweight,
functional observer pattern that prioritises composition and granular control
over state changes.

\subsection{An Enhanced Observer Pattern}
The core abstraction of the framework is the \kotlin{Observable<T>} interface.
Unlike standard observer implementations that often enforce rigid class
hierarchies, this framework defines a minimal contract focused on the
subscription mechanism.

\code{Kotlin}{listings/Observable.kt}{The simplified Observable contract}{observable}

As shown in \Cref{lst:observable}, the \kotlin{onChange} method requires a
\emph{registrant} (of type \kotlin{Any}) alongside the callback function. This
design choice decouples the identity of the subscriber (herein referred to
interchangeably as \emph{subscriber}, \emph{registrant}, \emph{observer} or
\emph{listener}) from the behaviour defined in the callback, allowing any
component to manage its subscriptions explicitly without implementing specific
listener interfaces. While the interface extends \kotlin{Disposable} to support
resource management, the implications of lifecycle management and the
prevention of memory leaks will be detailed in \Cref{ssec:disposability}.

To enforce strict control over state changes, the framework applies the
\emph{Interface Segregation Principle} (ISP)~\cite{martin2003agile} by
splitting read and write capabilities. The base \kotlin{Observable<T>} provides
a read-only view of the data stream, ensuring that consumers cannot
inadvertently alter the state of the source. State mutation is reserved for the
\kotlin{MutableObservable<T>} subtype. This interface extends the contract by
exposing an \kotlin{update} function, which encourages functional state
transitions of the form \kotlin{(T) -> T}. This distinction allows the internal
logic of a component to mutate state safely while exposing only the immutable
\kotlin{Observable} interface to external observers, preserving encapsulation.

\paragraph{Monadic Composition and Data Flow}
A primary advantage of this reactive approach is the ability to model complex
behaviours through the composition of simple event sources. Drawing inspiration
from functional programming and category theory, the framework treats
\kotlin{Observable} as a \emph{Monad}.

Through the basic uplifting operation \kotlin{fun observe(value: T):
	Observable<T>} and the set of extension functions defined in the framework,
developers can chain operations using standard functional operators:
\begin{itemize}
	\item \texttt{map} which transforms the emitted values of an observable,
	      creating a new derived stream;
	\item \texttt{flatMap}/\texttt{switchMap} with the goal to project each
	      emitted value into a new observable and flatten the resulting streams,
	      allowing for dynamic dependency replacement.
\end{itemize}
This monadic structure allows for the definition of complex data flows where
dependencies are handled implicitly. For example, a reaction's firing rate can
be defined as a transformation of local concentration values: as the
concentrations change, the derived rate updates automatically, propagating the
new value down the chain.

\subsection{Reactive Collections and Aggregation}
While standard observables handle scalar values efficiently, simulating a
pervasive ecosystem requires tracking aggregates, such as the list of
neighbours or the map of molecules within a node. To address this, the
framework introduces specific reactive collections: \kotlin{ObservableList},
\kotlin{ObservableSet} and \kotlin{ObservableMap}.
These interfaces provide granular observation capabilities. For instance,
\kotlin{ObservableMap} allows observing the value of a specific key, while
\kotlin{ObservableSet} allows observing the membership status of a specific
element. However, the true power of these collections lies in their ability to
perform \emph{complex aggregation} over dynamic content.

\paragraph{Aggregating Dynamic Streams}
In a simulation, an aggregate value (e.g. the total concentration of a
molecule across all neighbours) depends on two distinct factors:
\begin{enumerate*}[label=(\roman*)]
	\item \emph{structural changes} with neighbors entering or leaving the list
	      and
	\item \emph{element changes} where the concentration value changing within
	      an existing neighbor.
\end{enumerate*}

To handle this dual dependency, the framework provides sophisticated operators
such as \kotlin{combineLatest} for lists. This operator transforms an
\kotlin{ObservableList<T>} into a single \kotlin{Observable<R>} by applying a
mapping function \kotlin{(T) -> Observable<S>} to each element and then
aggregating the results. Crucially, the resulting stream emits a new value
whenever the list structure changes \emph{or} whenever any of the inner
observables emit a change. This allows to express through Alchemist global
properties (e.g. field strength or crowd density) continuous signals
derived purely from the local state of individual nodes.

The names and behaviours of such operators is largely inspired by
\textsc{ReactiveX}
operators\footnote{\url{https://reactivex.io/documentation/operators.html}}.

\subsection{Handling Optionality: Native Null-Safety versus Monadic Options}
A notable detail in the implementation of the reactive framework is the
adoption of the \texttt{arrow.core.Option} type over Kotlin's built-in nullable
types (\texttt{T?}).

In a pure Kotlin environment, the language's native null-safety features (via
the \texttt{?} operator and smart casts) are typically preferred for their
zero-overhead runtime representation and syntactic convenience. However, the
Alchemist simulator operates as a polyglot environment, integrating components
written in Java, Kotlin and Scala (e.g. the ScaFi incarnation). This
necessitates a more robust strategy for handling value absence for two primary
reasons:

\begin{enumerate}
	\item \emph{Semantic Distinction in Streams:} In a reactive data flow, it
	      is often necessary to distinguish between ``the value is known to be
	      null'' and ``there is no value yet'' (or ``the value has been
	      removed''). Kotlin's \texttt{T?} collapses these states. For instance,
	      in \texttt{ObservableMap}, retrieving the value for a specific key
	      returns an \texttt{Observable<Option<V>>}. This signature allows the
	      stream to explicitly signal three distinct states:
	      \begin{itemize}
		      \item \kotlin{Some(v)}: The key is present with value $v$;
		      \item \kotlin{Some(null)}: The key is present and the value is
		            explicitly null (if $V$ is nullable);
		      \item \kotlin{None}: The key is missing from the map.
	      \end{itemize}

	\item \emph{JVM Interoperability:} While Kotlin's nullable types are
	      effective within Kotlin sources, they are represented as standard
	      references (with metadata annotations) at the bytecode level. When
	      accessed from Java or Scala, the strict compile-time safety guarantees
	      are often lost or require verbose defensive programming. By using an
	      explicit monadic wrapper like \kotlin{arrow.core.Option}, we expose a
	      consistent \ac{API} across all \ac{JVM} languages. This aligns with the
	      functional paradigms of Scala (which relies heavily on its own
	      \texttt{Option}) and provides a richer, composable interface (e.g.
	      \texttt{map}, \texttt{flatMap}, \texttt{fold}) than standard Java null
	      checks.
\end{enumerate}

Consequently, while the use of an external library introduces a dependency
overhead, the semantic precision and interoperability benefits of
\texttt{arrow.core.Option} outweigh the simplicity of native nulls in this
specific architectural context.

\subsection{Optimising derived-observable values}
While the \kotlin{Observable<T>} interface defines the contract for data
consumption, the framework's efficiency lies in how these streams are
transformed and combined. The implementation of the aforementioned operators
like \kotlin{map}, \kotlin{filter} and \kotlin{mergeWith} relies on the
abstraction of \kotlin{DerivedObservable<T>}. This class manages the complexity
of state synchronisation and lifecycle management specifically addressing the
tension between the \emph{eager} consistency required by the \ac{DES} scheduler
and the desire for \emph{lazy} computation to minimise overhead and improve
resources usage.

\paragraph{The Challenge of Simulation Initialisation}
Alchemist divides its lifecycle into two distinct phases. The first is the
\emph{set-up phase}, where the environment is instantiated, nodes are created,
and reactions are wired to conditions. The second is the \emph{execution
	phase}, where the simulation loop begins.

This separation poses a challenge for reactive programming. When defining a
reaction during the set-up phase, a programmer might attempt to create an
observation stream on a component that is not yet fully initialised. For
instance, observing a node's position before the node has been deployed into
the environment will trigger a runtime error if the observation is evaluated
eagerly.

To address this, the framework offers two strategies:
\begin{enumerate}
	\item \emph{Deferred Creation:} Creating eager event streams only within
	      the \kotlin{initializationComplete} method of the \kotlin{Actionable}
	      interface. This guarantees that the stream is constructed only after the
	      set-up phase concludes and all components are stable;
	\item \emph{Lazy Subscription:} Creating event streams in the constructor
	      but deferring their activation. The stream remains inert during the
	      set-up phase and begins emitting values only when the simulation starts.
\end{enumerate}
To support the latter approach, the \kotlin{onChange} signature includes an
\kotlin{invokeOnRegistration} flag. When set to \kotlin{false}, it signals that
the registration should not trigger an immediate propagation of the current
value. This allows the dependency graph to be constructed safely during the
set-up phase without triggering premature computations on uninitialised data.

\paragraph{Smart Activation in Derived Observables}
The \kotlin{DerivedObservable<T>} class leverages this mechanism to implement a
``smart'' activation strategy that optimises both the computational graph and
resource usage.
A naive implementation of a reactive operator (e.g. \kotlin{map}) might simply
forward every downstream subscription to the upstream source. In a system with
many observers, this would lead to a \emph{subscription explosion}, where the
upstream source manages an excessive number of redundant listeners.

Instead, \kotlin{DerivedObservable} acts as a \emph{multiplexer}. It maintains
a single active subscription to its upstream source, regardless of how many
downstream observers are registered. When the upstream emits a value, the
derived observable computes the transformation once and multicasts the result
to all its subscribers. This significantly reduces the cardinality of the
dependency graph and the overhead of listener traversal.

Crucially, \kotlin{DerivedObservable} is \emph{inert} by default. It does not
subscribe to its upstream source until at least one observer registers with it.
If a derived stream is defined but never observed, it consumes no CPU cycles
and attaches no listeners to the source. This behaviour is managed via the
\kotlin{startMonitoring} and \kotlin{stopMonitoring} lifecycle hooks, which are
automatically invoked based on the emptiness of the subscribers list.

\paragraph{Explicit Initialisation and Safety}
Finally, the framework addresses the semantic ambiguity of ``initial values'' in
push-based systems. As highlighted in \cite{bainomugisha2013SRP}:
\begin{quote}
	``In push-based approaches, the programmer must initialise behaviours
	explicitly to make sure they hold a value when eagerly evaluating code in
	which they are used.''
\end{quote}

To strictly adhere to this principle, \kotlin{DerivedObservable} wraps its
internal state in an \kotlin{Option<T>}. This allows the framework to
distinguish between ``the stream has not yet yielded a value'' (\kotlin{arrow.core.None}) and ``the
stream yielded a null value'' (\kotlin{Some(null)}).

This distinction is vital for complex aggregators like \kotlin{combineLatest}.
If a derived stream attempts to aggregate an empty collection of observables,
it cannot compute a valid fresh value. Instead of blocking or throwing an
exception, the framework returns \kotlin{None}. This signals to downstream
consumers that the behaviour is defined but currently holds no value, allowing
the simulation to proceed without glitches until the necessary data becomes
available.

\subsection{\texttt{Disposable} pattern and Resource Management through
	Lifecycles}\label{ssec:disposability}

In a reactive architecture heavily reliant on the observer pattern, memory
management becomes a critical concern. As established in
\Cref{ssec:reactive_alchemist_principles}, the simulation graph involves
thousands of long-lived objects (Nodes, Molecules) and possibly short-lived
reactive streams. If an observer registers a callback on a long-lived subject
but fails to deregister when it is no longer needed, the subject \emph{retains}
a strong reference to the observer, preventing garbage collection. In the
context of Alchemist, this ``Lapsed Listener problem'' could quickly lead to
the progressive memory exhaustion over the course of a simulation.

To mitigate this, the framework introduces a structured \emph{lifecycle}
management system largely inspired by the Android Jetpack
architecture\footnote{\url{https://developer.android.com/jetpack/androidx}}.
This system automates the management of subscription ensuring that reactive
connections are severed automatically when the participating entities reach the
end of their lifecycle.

\paragraph{Design Rationale: Explicit Disposal versus Weak References} In
standard software architecture, a common countermeasure to the Lapsed Listener
problem is the employment of \emph{weak references}. By holding observers via a
\texttt{WeakReference} or storing them in a \texttt{WeakMap}, a system allows
the \ac{GC} to reclaim the subscriber if no other strong references
to it exist, effectively automating the cleanup process.

However, this approach was deliberately rejected for the Alchemist reactive
engine due to two primary constraints:

\begin{enumerate}
	\item \emph{Cross-Platform Consistency (Kotlin Multiplatform):} Alchemist
	      is evolving towards a multi-platform ecosystem (targeting JVM,
	      JavaScript and Native). The semantics and capabilities of weak
	      references vary drastically across these targets:
	      \begin{itemize}
		      \item On the \ac{JVM}, \texttt{WeakHashMap} allows iteration over keys,
		            which is essential for a subject to traverse its list of
		            subscribers and emit notifications;
		      \item In JavaScript, the \texttt{WeakMap} specification expressly
		            forbids iteration (keys are not enumerable) to ensure deterministic
		            garbage collection behavior. This makes it impossible to implement
		            a standard \emph{Observer} pattern where the subject iterates over
		            a collection of weak subscribers;
		      \item In Kotlin/Native, support for weak references has historically
		            been experimental or inconsistent with managed runtime
		            expectations\footnote{\url{https://youtrack.jetbrains.com/issue/KT-48075}}.
	      \end{itemize}
	\item \emph{Performance Predictability:} Weak references introduce
	      non-negligible overhead to the \ac{GC} and reference access.
	      Furthermore, relying on \ac{GC} for cleanup introduces non-determinism:
	      a ``dead'' listener might continue to receive events (and consume CPU
	      cycles) until the \ac{GC} actually runs. In a strictly deterministic
	      simulation engine, resource release should be explicit and tied to the
	      simulation model's lifecycle, not the \ac{JVM}'s memory pressure.
\end{enumerate}

Consequently, we opted for the \emph{Lifecycle} pattern described below. While
this requires more explicit architectural structure (i.e. components must
implement \texttt{Disposable} and explicitly manage and signal about their
lifecycle's state changes), it ensures deterministic resource management and
guarantees consistent behavior across all compilation targets.

\paragraph{Lifecycle-Aware components} At the lowest level, the framework
defines a functional interface \kotlin{Disposable} which provides a uniform
contract for any entity holding resources that must be explicitly released.
Core domain entities, including \kotlin{Node} and \kotlin{Reaction}, implement
this interface. When a node is disposed, it recursively dispose every reaction
attached to it and every reaction in turn dispose their conditions. This
explicit cascading cleanup is the first line of defense against leaks. While
this manual disposal is effective, it is error-prone if relied upon for every
individual subscription. To automate this, the concept of \emph{Lifecycle-aware
	components} is introduced. The architecture revolves around three key
abstractions:
\begin{itemize}
	\item \kotlin{LifecycleState} is a simple enumeration defining the valid
	      states of a component. At the time of writing, the states
	      \kotlin{INITIALIZED}, \kotlin{STARTED} and \kotlin{DESTROYED} are
	      defined; however, further works could enrich this set of states to
	      include finer-grained states both for better debugging purposes or
	      better subscription's state management (see the \textsc{AndroidX}
	      implementation for reference);
	\item \kotlin{LifecycleOwner}'s contract is implemented by any class
	      that has a defined lifecycle (e.g. \kotlin{Node},
	      \kotlin{Actionable}). It exposes an explicit \kotlin{Lifecycle}
	      object;
	\item \kotlin{Lifecycle} and \kotlin{LifecycleRegistry} are the actual
	      state managers which notifies state observers when the state
	      transitions occur.
\end{itemize}

The most powerful feature of this system is the integration between
\kotlin{Observable} streams and \kotlin{LifecycleOwner}s. The framework
provides the extension method \kotlin{bindTo} which wraps a standard
subscription in a lifecycle-aware ``safety harness''.
%
\code{Kotlin}{listings/bindTo.kt}{Wrapping an observable's standard
	subscription into a lifecycle-aware subscription}{bindTo}
%
The \kotlin{bindTo} (defined as in \Cref{lst:bindTo}) method performs three critical
functions:
\begin{enumerate}
	\item \emph{Pre-check:} If the owner is already \kotlin{DESTROYED}, the
	      subscription is ignored entirely, preventing ``zombie''
	      callbacks on dead objects.
	\item \emph{Active State Gating:} The callback is invoked \emph{only}
	      if the owner is in an active state (at least \kotlin{STARTED}).
	      This prevents reactions from firing while a node is still
	      initialising or paused.
	\item \emph{Auto-Unsubscription:} The operator registers an observer on
	      the owner's lifecycle. When the owner transitions to
	      \kotlin{DESTROYED}, the operator automatically calls
	      \kotlin{stopWatching()} on the data stream and removes itself.
\end{enumerate}

\paragraph{Application in the Engine}
This mechanism is ubiquitous in the new engine implementation. For example,
\kotlin{Actionable} (Reactions) implements \kotlin{LifecycleOwner}. When a
reaction subscribes to a condition (e.g. a molecule concentration), it uses
\kotlin{bindTo(this)}.

Consequently, when the \kotlin{Engine} removes a node from the environment, it
simply calls \kotlin{node.dispose()}. This triggers the following cascade:
\begin{enumerate}
	\item The Node marks itself as \kotlin{DESTROYED}.
	\item The Node disposes its Reactions.
	\item The Reactions mark themselves as \kotlin{DESTROYED}.
	\item The \kotlin{bindTo} bindings detect the state change and
	      unregister the Reactions from all upstream Observables (e.g.
	      neighborhood lists, molecule maps).
\end{enumerate}

This architecture guarantees that removing an entity from the simulation graph
cleanly prunes all its incoming and outgoing links, solving the memory leak
problem by design rather than by convention.

\section{Integration into Alchemist}
The implementation of the reactive framework described so far, provides the
necessary primitives to construct a reactive system. However, integrating these
primitives into a mature, production-grade simulator like Alchemist presents
significant software engineering challenges. The core architecture of Alchemist
relies heavily on imperative state queries (e.g.
\texttt{node.getConcentration(molecule)}), which permeate the entire codebase,
from the core engine to the various incarnation definitions.

This section details the strategy employed to refactor the Alchemist core, the
resulting simplification of the simulation engine and the practical adaptation
of existing model components.

\subsection{Integration Strategy: The \texttt{current} Bridge}
Refactoring the core \ac{API} of a simulator implies a fundamental shift in how
data is accessed. The transition from a \emph{pull-based} \ac{API} (getters) to
a \emph{push-based} \ac{API} (observables) introduces a dichotomy in
implementation strategies:

\begin{enumerate}
	\item Rewriting all consuming logic to be fully asynchronous and
	      callback-driven. While ideal for reactivity, this approach is
	      infeasible for a codebase of Alchemist's size, as it would require
	      rewriting the internal logic of every condition, action and incarnation
	      interpreter simultaneously.
	\item Exposing reactive streams while retaining synchronous access to the
	      current state.
\end{enumerate}

We adopted the second strategy. As defined in the \texttt{Observable<T>}
interface, every reactive stream exposes a \texttt{val current: T} property.
This design choice serves as a crucial architectural bridge. It allows legacy
components (such as the Protelis interpreter or existing unit tests) to
continue ``polling'' the state by accessing te \texttt{current} property,
maintaining semantic compatibility with the old \texttt{get()} methods.
Simultaneously, it allows the Engine and new components to subscribe to
\texttt{.onChange} to leverage the reactive capabilities.

\paragraph{Reactive Caching}
Beyond simple state access via \kotlin{current}, this strategy enables a hybrid
implementation pattern where components maintain an internally reactive state
while exposing a synchronous, poll-based \ac{API}. This is particularly
valuable for retrofitting conditions which required a synchronous
\kotlin{isValid(): Boolean} method.

Consequently, the core \texttt{Node} and \texttt{Environment} interfaces were
refactored to replace standard getters with observable providers. This allows a
gradual migration where the \emph{structure} of the simulator is reactive (the
engine subscribes to changes), but the \emph{internal logic} of reactions can
still operate imperatively on the current state if needed.

\subsection{The Engine Simplification}
The most significant architectural benefit of this integration is the radical
simplification of the \texttt{Engine}. In the legacy implementation, the engine
was a monolithic supervisor responsible for
\begin{enumerate*}[label=(\roman*)]
	\item extracting the next event from the queue,
	\item executing the reaction,
	\item manually traversing the dependency graph to identify affected
		reactions and finally
	\item recalculating propensities and updating the scheduler.
\end{enumerate*}
In the new reactive implementation, the Engine's responsibilities are reduced
strictly to \emph{scheduling} and \emph{execution}. The logic for
dependency tracking and invalidation is entirely offloaded to the reactions
themselves via the \kotlin{rescheduleRequest} stream.

The simplified logic of the reactive engine can be summarized in the
\kotlin{scheduleReaction} method, shown in \Cref{lst:engine_schedule}: the
Engine no longer queries the environment to see if a reaction needs an update.
Instead, it subscribes to the reaction's \kotlin{rescheduleRequest} observable.
This signal is emitted autonomously by the reaction whenever one of its
observed dependencies changes.

\code{kotlin}{listings/scheduleReaction.kt}{The reactive scheduling logic in \texttt{Engine}}{engine_schedule}

The flow proceeds as follows:
\begin{enumerate}
	\item Upon initialization, the Engine registers itself as a listener to the
	      \kotlin{rescheduleRequest} of every reaction;
	\item The scheduler pops the reaction with the minimum $\tau$ (time) and
	      executes it;
	\item The reaction execution modifies the environment (e.g. changing a
	      concentration in a Node);
	\item The modified Node notifies its observable contents and properties.
	      These updates propagate synchronously through the graph of dependencies
	      defined by reactions' conditions;
	\item Dependent reactions receive the update, re-evaluate their
	      conditions/rates, and if a change in scheduling is required, they emit
	      a signal on their \kotlin{rescheduleRequest} stream;
	\item The Engine receives the signal and updates the reaction's position in
	      the priority queue.
\end{enumerate}

This flow eliminates the need for the Engine to understand \emph{why} a
reaction needs rescheduling: it simply responds to the request.

\subsection{Reactive Dependencies Declaration}
In Alchemist, dependencies are expressed through the mechanisms illustrated in
\Cref{ssec:alchemist_engine}. Moreover, the granularity of dependencies can be
further refined explicitly using the \kotlin{Dependency} mechanism, which
identifies the specific molecule or set of molecules a reaction depends on.
With this information, the Engine updates the dependency graph to accurately
model dependencies on molecule concentrations, neighbor positions, node
contents or global states.

Specifically, a reaction's inbound dependencies are declared within its
conditions, as these define which domain elements trigger a rescheduling. While
this model fits the legacy Alchemist API, adapting it to a reactive
implementation requires a shift in design.
In particular, dependencies are now expressed in terms of the reactive streams
a reaction is ``interested in''. Each condition exposes a set of dependencies
(i.e. observable data streams) that are merged and observed by the enclosing
reaction. Through this mechanism, a reaction triggers a reschedule request
whenever an update is emitted by this merged stream. By modeling dependencies
as observables rather than static tokens, the system achieves the inversion of
control typical of reactive architectures: updates propagate from data sources
to the scheduler, rather than requiring the engine/scheduler to poll for
changes.

This approach extends naturally to wider dependency contexts, such as
neighborhoods or global state, as the framework supports the observation of
aggregate structures (e.g. node positions, contents, or the entire
environment).

\subsection{Verification of Correctness}
